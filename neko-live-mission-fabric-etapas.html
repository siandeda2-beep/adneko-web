NEKO LIVE MISSION FABRIC
Historial de desarrollo por etapas

Registro cronológico y técnico del trabajo acumulado en la infraestructura de misiones de NEKO. Distingue construcción, pruebas locales, ejecución real, integración de código y certificación operativa, sin convertir un PASS parcial en certificación de producción.

Corte: 18 de octubre de 2026 · Proyecto: NEKO LIVE MISSION FABRIC · Repositorio: siandeda2-beep/adneko · Rama de integración: feature/neko-live-host-once-20261017

Resultado acumulado al corte.

El núcleo de misiones, persistencia, reservas, validación de evidencias y transporte Remote V3 está desarrollado. Se reportó y documentó una primera misión real Windows con respuesta PASS. Posteriormente se consolidaron componentes, se endurecieron los gates del host, se incorporó el soporte de tres slots Codex y se fusionó el contrato durable Codex–Mission. La ejecución concurrente real de tres agentes, la identidad autenticada de tres cuentas distintas y la operación sostenida de extremo a extremo no estaban certificadas en este corte.

Etapa 1 · Arquitectura y contrato de misiones

CONSTRUIDA
  • Definición de Mission Fabric como capa de coordinación de objetivos autorizados: misión, tareas, dependencias, reservas, permisos y estados.
  • Separación de responsabilidades: NEKO Brain interpreta objetivos; Agent Orchestrator coordina sistemas; Mission Fabric gestiona ejecución y evidencia; NEKO Remote V3 transporta solicitudes autorizadas a Windows.
  • Implementación del modelo persistente de misiones, eventos, snapshots y control de revisión/CAS.
Base técnica: tools/neko-mission/mission.mjs, store.mjs y documentación de Mission Fabric en el repositorio.

Etapa 2 · Motor, scheduler, reservas y validación

PASS DE COMPONENTES
  • Implementación de despacho acotado, reserva de tareas, correlación de solicitudes e idempotencia.
  • Incorporación del flujo read-cycle y la verificación de recibos Remote V3 antes de registrar resultados PASS.
  • Certificación nativa reportada en Windows con Node 22.16.0: 122/122 pruebas PASS sobre el commit b7ea2253.
Evidencia: recibo de pruebas nativas en GitHub. El PASS corresponde al alcance ejecutado en ese commit.

Etapa 3 · Primera misión LIVE hacia Windows

PASS OPERACIONAL REPORTADO
  • Mission Fabric generó una solicitud LIVE autorizada workspace-info y la entregó mediante NEKO Remote V3.
  • El host Windows devolvió respuesta PASS, exitCode 0, con correlación de solicitud y recibo.
  • Se demostró la comunicación real para esa operación; no supone operación autónoma continua.
Evidencia: recibo operacional Windows en GitHub.

Etapa 4 · Consolidación de la cadena Mission Fabric

CÓDIGO INTEGRADO
  • Consolidación de dependencias y trabajo asociado a los PR #148, #149 y #155, conservando el código certificado según el checkpoint de coordinación.
  • Se mantuvo separado el avance del código de la certificación de operación sostenida.
Alcance: consolidación técnica reportada; no significa que todos los PR citados estén individualmente fusionados a main.

Etapa 5 · Supervisor Windows y endurecimiento de gates

FUSIONADO EN RAMA DE INTEGRACIÓN
  • Supervisor host-once con exclusión de ejecución mediante lease local.
  • Mejoras de diagnóstico y sanitización de errores: PR #168 y #173.
  • Endurecimiento de Native Gate, procesos y pruebas: PR #171.
  • Pruebas locales reportadas tras PR #173: 21/21 de host y 171/171 de Native Gate PASS.
Límite: el fallo anterior del lanzador PowerShell PR #158 (PR158_GATE_INTERNAL_FAILED) no tiene cierre demostrado; la certificación del supervisor en operación sostenida sigue pendiente.

Etapa 6 · Tres slots Codex y ejecución vinculada a Mission

B1 + B2 FUSIONADOS
  • B1: soporte de hasta tres slots Codex, con worktrees y CODEX_HOME independientes y rechazo de configuraciones fuera del límite; PR #169.
  • B2: registro durable de inicio y resultado COMPLETED_UNVERIFIED, enlazado a misión, reserva, intento, slot, participante, worktree y requestId.
  • Persistencia de hash y tamaño de respuesta sin almacenar el texto; protección fail-closed ante ejecución incierta tras reinicio; PASS solo tras evidencia Remote V3 validada.
  • Codex 3 reportó 138/138 pruebas locales PASS con dobles controlados. PR #175 fusionado en la rama autorizada; sus 10/10 blobs se comprobaron después de la fusión.
Commit de integración B2: 8549ecc15463aac5d53dc7b1f4fd8362c33dd03e. Los dobles controlados no certifican tres cuentas reales.

Etapa 7 · Recuperación controlada y límites conocidos

B5 PASS CONTROLADO
  • ChatGPT 3 reportó pruebas sintéticas de locks huérfanos en almacenamiento y host: EEXIST y HOST_LOCK_BUSY_OR_RECOVERY_REQUIRED.
  • Snapshot, revisión, reserva, requestId y claves de idempotencia conservados; reanudación tras retirada manual controlada del lock.
  • No se modificó código: la recuperación manual conservadora es el diseño actual. No existe recuperación automática tras crash certificada.
Registro de B5: informe E3-07E en GitHub; ejecución reportada, sin TAP independiente adjunto.

Etapa 8 · Concurrencia real y cierre integral

EN DESARROLLO / PENDIENTE
  • E3-08A: implementación y prueba de tres tareas concurrentes con ejecutores controlados. Al corte se había actualizado el checkout al merge B2 y emitido la instrucción de implementación; todavía no existía resultado PASS de esta etapa.
  • B4: codex login status detecta sesión, pero no demuestra que tres perfiles correspondan a tres cuentas autenticadas distintas. Requiere mecanismo confiable y oficialmente soportado.
  • Faltan demostrar ejecución periódica autónoma, operación sostenida, recuperación de fallos integrada, tres agentes Codex reales y E2E conjunto de Agent Orchestrator + Mission Fabric + Remote V3 con misiones de varios pasos.
  • Las capacidades de colaboración ampliada, voz, móvil y continuidad offline permanecen en el alcance evolutivo; este checkpoint no las declara certificadas.
Estado al 18/10/2026: pendientes operativos, no defectos automáticamente atribuidos a los módulos que ya aprobaron sus pruebas.
